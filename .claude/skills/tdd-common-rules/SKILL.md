# Common engineering rules

Shared by all coding agents (test-writer, implementer, refactorer).
Each agent adds its own stage rules on top of this file. If an agent's
instructions and this file conflict, stop and ask the engineer.

## Source of truth

- Approved business behavior: the analyst's acceptance criteria and
  `behaviour-decisions.md`.
- Approved engineering choices: `engineering-decisions.md`.
- Read both before designing or changing anything.

## Decision recording

- `engineering-decisions.md` is append-only. Never edit or delete earlier
  entries; a changed decision is a new entry that supersedes the old one.
- Append a timestamped entry (with UTC offset) before relying on a new
  explicit engineer decision. If the original decision time is unknown,
  record the entry time and mark it retrospective.
- Label recommendations and unapproved design choices as proposals. Never
  turn a proposal into a requirement or a decision silently.

## Changing guidance

- Do not edit this file, any agent file under `.claude/agents/`, or any
  skill file without engineer approval. Propose the change with its reason,
  then wait.
- When engineer feedback reveals a reusable rule, propose where it belongs:
  this file if it applies to every coding agent, otherwise the one agent
  file that needs it.

## Repository boundaries

- Work in the engineer's checkout on the active pilot branch. Do not
  create, switch, or delete branches without engineer approval.
- Keep all coding artifacts under the pilot's `coder` directory; analyst
  artifacts stay under `analyst`.

## Behavior versus design

- Acceptance criteria belong to the analyst. Do not edit them; if a
  criterion looks wrong, incomplete, or contains a technical mechanism, stop
  and ask the engineer.
- Record approved technical decisions (exception types, signatures, data
  structures, algorithms, frameworks) in the decision log and the design
  document. Link from the design to the criterion they serve, never the
  other way round.
- The approved design is the overall target, not permission to build all of
  it at once. Let the current failing test drive each change.
- Test observable behavior separately from the API contract that exposes
  it. For example, "a new item is rejected and state is unchanged" is one
  test; "the rejection throws a specific exception type" is another.

## Commits and approval gates

- Work one acceptance criterion at a time: RED, then GREEN, then an
  optional REFACTOR.
- During the pilot, commit the failing RED test on its own, so the engineer
  can review the test before any implementation exists. This is a
  pilot-only exception to the README's advice against leaving a branch
  broken for a RED commit. The target workflow combines RED and GREEN in
  one commit.
- Commit subject: `<short behavior name> [RED]`, `[GREEN]` or `[REFACTOR]`.
  Use the same behavior name for every commit of a criterion.
- Stop for engineer approval after every commit. Do not start the next
  stage or criterion until the previous commit is approved.
- Keep each commit focused on its stage. Include a design or decision-log
  change in the commit it explains only when directly related; keep
  unrelated documentation out of TDD commits.

## Evidence and handoff

- Do not claim a result (tests passing, target met, behavior guaranteed)
  without evidence from a command you ran.
- When handing off, report the commands run and their outcomes, any
  unapproved decisions, and any unresolved risks.
